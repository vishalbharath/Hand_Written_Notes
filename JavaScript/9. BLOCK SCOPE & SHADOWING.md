
### BLOCK 

- A block is also Know as **Compound Statement**
- A **block** is any group of statements wrapped in `{ ... }`
- Blocks appear in `if`, `for`, `while`, and plain grouped `{ }`.
- block itself does **not** create a new _function_ scope — but with ES6 it _does_ create a new **block scope** for `let` and `const` declarations (unlike `var`)
```javascript

// block example
{
  // this is a block
  let x = 10;    // x is block-scoped
  var y = 20;    // y is function/global-scoped (not block-scoped)
}
console.log(typeof x); // "undefined"  (x is not visible outside block)
console.log(typeof y); // "number"     (y leaked to outer scope if not inside a function)


```


### BLOCK SCOPE

- `let` and `const` are **block-scoped** — they live only inside the nearest `{ ... }`.
- `var` is **function-scoped** (or global if not in a function). `var` ignores block boundaries (except functions
- `let`/`const` also introduce a **Temporal Dead Zone (TDZ)** — you cannot access them before their initialization (accessing earlier produces a `ReferenceError`).
```javascript

function demo() {
  if (true) {
    console.log(a); // undefined  (hoisted var)
    console.log(b); // ReferenceError if uncommented — b is in TDZ (not hoisted for use)
    var a = 1;
    let b = 2;
  }
}
demo();


```

### Lexical scope & the scope chain

- **Lexical scoping** means the scope of a variable is determined by the _physical placement_ of the code — where functions and blocks are written — not by how/where they are called at runtime. 
- When code tries to resolve an identifier, JavaScript looks **up the scope chain**: inner → immediately enclosing → next outer → ... → global. That chain is fixed at function creation time (hence _lexical_).

```javascript

function outer(name) {
  const greeting = `Hello, ${name}`;
  return function inner() {   // inner closes over `greeting`
    console.log(greeting);
  };
}

const sayHi = outer('Alice'); // outer runs and returns inner
sayHi(); // "Hello, Alice"  — inner remembers outer's lexical environment


```

Here `inner` uses variables from the lexical (enclosing) scope where it was defined, even after `outer` has returned — that's a _closure_.


### Shadowing (normal, expected behavior)



**Shadowing** happens when an inner scope declares a variable with the same name as an outer-scope variable. The inner variable _hides_ the outer one inside the inner scope.

```javascript

let x = 1;
{
  let x = 2;    // shadows outer x
  console.log(x); // 2
}
console.log(x); // 1  (outer x unchanged)


```

Shadowing is common and generally allowed (and useful) — inner identifiers simply take precedence when resolving names in inner code. 


### Illegal shadowing

Some combinations of declarations are **not allowed** and will cause a syntax/parse error — that's called _illegal shadowing_. A common case:

- If a `let` or `const` (a lexical binding) exists in a given function scope, you cannot have a `var` declaration that would create/hoist a `var` binding into that _same_ function scope with the same name. The parser rejects that because `var` hoists to the function/global scope and would conflict with the lexical binding. The result is a `SyntaxError` (parse-time).
```javascript

function test() {
  let b = "outer";
  if (true) {
    // the `var b` would be hoisted to the function scope, colliding with `let b`
    var b = "inner"; // SyntaxError: Identifier 'b' has already been declared
  }
}


```

The JS engine refuses to parse that code because `var b` would create a function-scoped `b` while a lexical `b` already exists in the same function-scope scope. Note: this is a parse-time error — your script won't run.

###### Legal shadowing example (no error):

```javascript

var a = 1;
{
  let a = 2;    // allowed — let creates a new block-scoped binding that doesn't collide
  console.log(a); // 2
}
console.log(a); // 1


```

So: _let/const can shadow var in an inner block_, but _var cannot be used to shadow a lexical binding that already exists in the same function/global scope_ (that produces illegal shadowing).


### Temporal Dead Zone (TDZ) — a short note

- When you declare `let`/`const`, their bindings exist for the whole block from the start (for parsing) but are _uninitialized_ until the execution reaches the declaration. 
- Accessing them earlier throws a `ReferenceError`.
- This is the TDZ — a common source of bugs when converting old `var` code to `let`/`const`.
```javascript

{
  // TDZ for `foo` starts here
  // console.log(foo); // ReferenceError
  let foo = 5;       // TDZ ends after this line
  console.log(foo);  // 5
}


```

### Lexical block scope — practical examples (for loops and closures)

A classic pitfall: using `var` in a loop with asynchronous callbacks captures the _same_ `i` each iteration. `let` fixes that by providing a fresh binding each iteration.

```javascript

// BAD with var:
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log('var i:', i), 10);
}
// After loop finishes, i === 3, so all callbacks print "var i: 3"

// GOOD with let:
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log('let i:', i), 10);
}
// prints:
// let i: 0
// let i: 1
// let i: 2


```


`let` creates a fresh `i` binding per iteration (block scope per iteration) so closures see the value for that iteration.


### Arrow functions: scope & lexical this

Arrow functions (`() => {}`) follow the **same lexical scoping rules for variables**, but they _differ_ in how they bind `this`, `arguments`, `super`, and `new.target`:

- Arrow functions do **not** create their own `this`. They capture (lexically bind) `this` from the surrounding scope — often described as _lexical `this`_.
- Arrow functions also have **no `arguments` object** and cannot be used as constructors (cannot be called with `new`).
- They are great when you want to preserve the outer `this` inside callbacks.

```javascript

const obj = {
  value: 42,
  method1: function () {            // regular function: `this` is obj when called as obj.method1()
    setTimeout(function () {
      console.log(this.value);       // undefined (or global), `this` is not obj inside this callback
    }, 0);
  },
  method2: function () {
    setTimeout(() => {
      console.log(this.value);       // 42 — arrow uses lexical `this` (inherited from method2), so works
    }, 0);
  }
};

obj.method1(); // likely prints undefined
obj.method2(); // prints 42


```

Also, arrow functions are not hoisted like function declarations and are typically anonymous (you assign them to variables). Use them when you want a short expression and when you want the `this` from the outer scope.


### Quick checklist / TL;DR

- `{ }` = block. `let` & `const` are block-scoped; `var` is function/global-scoped. 
- Lexical scope = scopes are determined by code layout; closures capture outer variables.
- Shadowing = inner names hide outer ones (normal). 
- Illegal shadowing = certain mixes (e.g., a `var` whose hoisting would conflict with an already-declared lexical `let`/`const` in the same function/global scope) produce a syntax error.
- Arrow functions use lexical `this` and no `arguments`; they’re not suitable as constructors
